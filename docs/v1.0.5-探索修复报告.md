## 0. 摘要

### 0.1 问题现象（用户原话归纳）

1. 看着看着就停：只翻译开头一两句/几十秒后不再输出字幕，但状态栏还在一闪一闪"正在同传 / 监听音频中"；
2. 切语境后经常连不上/连接超时/一直重试；
3. 输出被拆成一个个词往外蹦，延迟高达十几秒；
4. 希望保留"语境模式 / 系统提示词宏观介入"（用户认为以前可以实现）。

### 0.2 最终结论：四层根因叠加

| 层 | 根因 | 决定性证据 |
|---|---|---|
| 1. 协议层 | v1.0.3 删掉了 v1.0.1 已修好的原生 `translationConfig`，退回「TEXT + systemInstruction」的普通 Live 会话载荷；翻译模型因此退化为稀疏/回合式输出 | 用真实网关实测：正确层级可 `setupComplete` 并持续输出；官方文档 WebSocket 示例的层级会被服务端以 **1007** 拒绝 |
| 2. 传输层（本次新发现，最隐蔽） | 音频帧用了 `realtimeInput.audio`，服务端几乎不连续处理；改为 `realtimeInput.mediaChunks` 后同一配置从 **2 条/120s** 变为 **30 条/120s**、p50 延迟≈**-49ms** | 同模型同 setup 的 A/B 对照日志 |
| 3. 会话层 | 长会话约 70~90s 后模型产出从 6~11 条/10s 塌缩到 0~1 条/10s（会话未断）；同配置多次连接方差 2~118 条 → 主因指向网关 5-Key 轮换绑定的上游 Key 质量 | 4 分钟长测 + 压缩版对照；最终对策是看门狗主动重连换 Key |
| 4. 连接层 | 12s 握手超时 vs 实测握手 1.7~23.1s；重连 5 次即永久停服；4xx/限流被误判致命 → 正常网络抖动被放大为"永远连不上" | slow-handshake 注入：v1.0.4 触发 `handshake timed out (12s)` → close 1006 → 重连 1/5，首条字幕推迟到 22.1s |

## 3. 理解阶段：读懂这个软件

### 3.1 官方文档抓取与"文档陷阱"

`web_fetch` 工具对 `ai.google.dev` 解析失败（非公网 IP），改用 PowerShell `Invoke-WebRequest` 直接抓取官方页面，再用 Python + lxml 提取正文，落盘为 `_takeover/docs/all_docs2.txt`。抓取了四份文档：

- Live Translation 指南（`live-api/live-translate`）
- 模型页（`models/gemini-3.5-live-translate-preview`）
- Live API 总览（`live-api`）
- WebSocket 入门（`live-api/get-started-websocket`）
- 额外抓取 REST 参考（`api/live`），用于核对 `BidiGenerateContentSetup` 字段表

**关键收获与陷阱**：官方 Live Translation 文档的 WebSocket JSON 示例把 `inputAudioTranscription`/`outputAudioTranscription`/`translationConfig` 全部放进 `generationConfig`；而 REST 参考里 `BidiGenerateContentSetup` 的字段表显示转写配置应在 **setup 顶层**。两者矛盾，必须在真实服务端裁决（见 §4.1）。

### 3.2 网关架构理解（`D:\ServerOps`）

从 `GEMINI_API_GATEWAY_SPEC.md` 提炼出对客户端真正有影响的事实：

- Nginx + Cloudflare，5 个 Google Key 通过 `split_clients` 做**无状态概率轮询**；扩展只需填占位 Key，网关在握手时注入真实 Key → **每条 WebSocket 连接固定绑定一个上游 Key**；
- `/ws/` 专用 location：`proxy_read_timeout 3600s`、支持 Upgrade；Cloudflare 前置（WS 支持，100s 空闲超时）；
- 因此"重连"在架构上等于"换一个上游 Key"，客户端绝不能因为 4xx/限流就永久放弃（与 v1.0.4 的行为冲突）；
- 网关可能因上游 Key 质量差异导致**同一客户端请求表现不稳定**，这为后来的"产出方差 2~118 条"提供了架构解释。

### 3.3 代码通读与版本考古

- 通读 v1.0.4 `content.js`（2053 行）：确认 8 条初始假设，并发现 `getBcp47LanguageCode`/`isLiveTranslateModel` 是**无调用点死代码**——暗示原生协议分支曾被删除。
- 提取 v1.0.0~v1.0.4 五个版本源码逐一 diff：
  - v1.0.1 `f094fdc` **新增**原生分支（`responseModalities:['AUDIO']` + `translationConfig`）；
  - v1.0.3 `ee26433` **整段删除**同一段代码 → 协议回归；
  - v1.0.0 与 v1.0.4 的两点 diff 中协议差异净变化为 0（先加后删），**只看最终 diff 会完全错过病因**。这是本次版本考古最重要的教训之一。
- 对比 `Gemini_Live_Translator_Baseline_v1.0.0`（78693 字节）与 `git show v1.0.0:content.js`（78696 字节），确认黄金基线≈v1.0.0。

## 4. 探索阶段：五个决定性实验

> 全部实验脚本与原始日志见 `_takeover/proto/`、`_takeover/e2e/`；本节只保留结论与关键数字。

### 4.1 实验一：setup 层级裁决（官方文档示例是错的）

**方法**：用 `probe_live.mjs` 依次发送三种 setup，只观察握手结果与 `serverContent`。

| 变体 | 结构 | 结果 |
|---|---|---|
| V0 官方文档写法 | 三个配置全放 `generationConfig` | ❌ close **1007**：`Unknown name "inputAudioTranscription" at 'setup.generation_config': Cannot find field.` |
| V1 旧脚本写法 | `translationConfig` 放 setup 顶层 | ❌ close **1007**：`Unknown name "translationConfig" at 'setup'` |
| **V5 正确形态** | `generationConfig:{responseModalities:["AUDIO"], translationConfig:{...}}` + **顶层** `inputAudioTranscription/outputAudioTranscription` | ✅ `setupComplete`（2.1s/3.1s…），随后持续收到 `inputTranscription`/`outputTranscription`/`inlineData`/`usageMetadata` |

**附加结论**：

- `systemInstruction` 在正确形态下**被接受但不生效**（官方明确翻译模型不支持 instruction）；
- `clientContent` 一发即 **1007 "Request contains an invalid argument."** 并断会话 → 任何时候都不能再向 native 翻译模型发文本转向（前任 v1.0.3 做过，属无效且有害）。

**产物**：`_takeover/proto/protocol_report.md` §2；日志 `logs/v0_*`、`logs/v1_top_*`、`logs/v5_*`、`logs/B_clientcontent_*`。

### 4.2 实验二：音频帧格式（本次最隐蔽、最关键的发现）

**方法**：固定其余变量（同一 native setup、同一 16.5s 循环语音、100ms/帧实时节奏），只切换 `realtimeInput` 的字段形态。

| 变体 | 帧格式 | 时长 | ORIG/OUT | 最大缺口 | 结论 |
|---|---|---|---|---|---|
| B | `realtimeInput.audio {data,mimeType}` | 120s | **2/2** | **77.4s 空白** | 几乎不连续 |
| D | `realtimeInput.mediaChunks [{mimeType,data}]` | 120s | **30/30** | 12.6s（后段递增） | 连续同传，p50 lag≈**-49ms** |
| P2 | 旧载荷（无 translationConfig）+ mediaChunks | 60s | 34/34 | — | 阳性对照 |
| P0-TEXT | native + TEXT + mediaChunks | 120s | 35/35 | 14.6s | TEXT 也连续，但无额度收益 |

**为什么这个发现重要**：`realtimeInput.audio` 是当前官方文档的主推字段，语法上完全合法、握手正常、也能偶尔出字——极易被误判为"模型本身就这样"。只有 A/B 对照才能发现它在这条链路上被稀疏处理。**这一条直接解释了"延迟十几秒、翻两句就停"中"字不连续"的部分。**

补充：`responseModalities:["TEXT"]` 并不能省额度——服务端仍持续返回 24kHz `inlineData` 译文语音，`usageMetadata` 也按 AUDIO 计数。因此 v1.0.5 保持官方推荐的 `AUDIO`。

### 4.3 实验三：长会话退化与上下文压缩

**现象**：4 分钟连续语音（无压缩）全程 alive（无 close/error），但约 **70~90s 后**产出从 6~11 条/10s 塌缩到 0~1 条/10s。这正是用户"看着看着就不翻译了"的直接机理之一。

**第一次尝试**：在 setup 顶层加入 `contextWindowCompression:{slidingWindow:{}}` 后，一次 120s 测试达到 **118/118 条**、每 10s 稳定 6~14 条、零 >4s 缺口（p50 lag≈-36.5ms），一度被当作解药。

**修正**：补跑 240s 压缩版只出 50 条（无压缩 4 分钟为 71 条），同配置多次连接在 120s 内产出方差达 **2~118 条**。结论修正为：

- `contextWindowCompression` 被服务端接受且无害，保留为优化；
- **不是稳定解**；主变量更可能是网关 5-Key 轮换绑定的上游 Key/后端质量；
- 落地对策改为**看门狗主动重连换 Key**：有语音 18s 无转写 / 原文流动但译文停 20s / 服务端 45s 静默 → 重建会话。重连恰好会命中网关另一个 Key，能绕开劣质上游。

**产物**：`logs/D_long120s_mediachunks.jsonl`、`logs/P0_4min_mediachunks.jsonl`、`logs/P0_120s_text_mediachunks.jsonl`、报告 §6。

### 4.4 实验四：连接策略与握手耗时分布

**握手采样**：`setupComplete` 耗时 n=24：**min 1.7s / median 3.07s / max 13.2s**；Lead 侧另见 13.4s、23.1s；另记录 1 次 WebSocket open 阶段 40s 卡死（TCP/TLS 阶段）。→ 12s 超时必须取消，30s 是必要下限；建连阶段也需要独立超时重试。

**真机故障注入**（chrome-e2e）：对 v1.0.4 注入 13s 网络延迟后：
- console 出现 `handshake timed out (12s)` → close **1006** → 重连计数 1/5 → 首条字幕推迟到 **22.1s**，恢复耗时 7.1s；
- 这精确复现了用户"切换语境/网络差时一直连接中"的体验。v1.0.5 改为 30s 分层超时 + 无限退避后，同条件不再误杀。

### 4.5 实验五：Chrome 真机 E2E（before/after）

**测试台**：Chrome 155 + CDP（Node 24 实现，无第三方依赖）加载未打包扩展 → 本地 HTTP 页面播放 366s 带音轨测试视频 → 每 2s 采样浮窗字幕/状态/WS 帧/console/截图 → 自动判定 verdict。

**网络诊断（本机专有，不影响扩展逻辑）**：
- 本机 Chrome↔Cloudflare 受 Mihomo TUN/fake-ip 影响，默认解析路径建连 1.2~8s 抖动、偶发 21s/1006；
- 用页面上下文直接建 WSS 的矩阵实验证明：**Origin/Cloudflare 没有拦截**（返回 HTTP 101、cf-ray LAX/NRT 正常），失败发生在连接建立阶段；
- 用 DoH 解析真实 Cloudflare IPv4 并 `--host-resolver-rules=MAP <host> <ip>` 后，握手稳定 **0.5~0.9s**。测试台因此内置"网络预检 + IP 映射"，避免把环境问题误判成扩展故障。

**主测结果（330s）**：

| 指标 | before v1.0.4 | after v1.0.5（最终冻结版） |
|---|---|---|
| 协议载荷 | TEXT + systemInstruction，无 translationConfig | 原生 translationConfig + 顶层 transcriptions + mediaChunks + compression |
| 扩展握手 / setupComplete | 1.6s | 499ms / 814ms |
| 330s 字幕提交 | 100 条 | **86 条**（多轮 79/89/86/90，受断句合并与上游质量影响） |
| 最长提交间隔 | 6.2s | **8.1s**（阈值 <20s） |
| 断连/重连 | 0（本机可靠网络） | **0**（closeCodes 为空） |
| 状态栏 | 随音量 500ms 变化 | 全程仅"🟢 正在同传"，1 次状态迁移 |
| 输出稳定性 | 100 条/330s | 每 30s 6~9 条，11 个时间桶无衰减 |

**重要结论**：在"可靠网络 + 连续语音 + 前台 tab"下，v1.0.4 其实也能连续翻译——所以用户故障不是稳定网络下的必然。真正放大因素是旧版 12s 超时 / 5 次重连上限 / 4xx 判死；而"字不连续、逐词蹦"与传输层帧格式、断句逻辑相关。修复必须同时覆盖协议、传输、连接与体验四层，这也解释了为什么前任"单点修复"总是无效。

## 6. 修复实现：v1.0.5 / v2 引擎

### 6.1 架构总览

`content.js` 由 2053 行重写为 2260 行（81.4KB → 92.7KB），采用四层架构：

```
┌──────────────────────────────────────────────────────┐
│ UI 层（Shadow DOM 浮窗）                              │
│  拖拽/缩放/透明度/字号/显示模式/音源/语境菜单/状态栏      │
├──────────────────────────────────────────────────────┤
│ 字幕引擎                                              │
│  inputTranscription + outputTranscription 增量合并      │
│  四重边界断句 → 零重排文本节点渲染 → 滚动跟随             │
├──────────────────────────────────────────────────────┤
│ 会话状态机                                            │
│  CONNECTING → READY → STREAMING → RECONNECTING         │
│  看门狗 / 无缝轮转 / goAway / 错误分级 / 无限退避        │
├──────────────────────────────────────────────────────┤
│ 音频引擎                                              │
│  <video>/麦克风 → AudioContext → 连续相位重采样 16k     │
│  → 精确 100ms Int16 分块 → Base64 → mediaChunks        │
└──────────────────────────────────────────────────────┘
```

### 6.2 会话状态机

- 会话对象化：`{id, ws, state, createdAt, readyAt, lastOrigAt, lastOutAt, rotationTimer, intentionallyClosed}`；旧回调以 `session !== activeSession` 守卫；
- 建连超时 30s（含 WS open 与 setupComplete 两阶段），超时只重建会话不判死；
- 断线 → 指数退避 600ms→8s 封顶 + ±20% 抖动，无限次重试；仅显式 `API_KEY_INVALID`/鉴权类错误终止；
- **看门狗**（每 2.5s）：服务端静默 45s、有语音但 18s 无转写、原文流动但译文停 20s、音频 5s 未发送 → 主动重建；
- **9 分钟无缝轮转**：先建 standby 会话，收到 `setupComplete` 后再切换音频源，旧会话随后关闭；`goAway` 按剩余时间提前轮转；
- 视频暂停时跳过"无转写/静默"判据，避免暂停期反复重连。

### 6.3 音频引擎

- 流式跨块重采样：保留上一块末尾 2 个采样 + 分数相位，输入块之间连续插值（修复旧版块间相位跳变与约 1.76s/小时的时间轴漂移）；
- 输出按 1600 采样（100ms）精确切块；`mediaChunks` 帧格式；100ms 节奏；
- `AudioContext.statechange` + 定时 resume；视频切换/SPA 导航自动重绑定；
- 弱网背压：`ws.bufferedAmount > 1MB` 丢弃最旧音频块；握手期最多缓存 3s 音频并在就绪后回放；
- 视频未就绪时进入"等待播放"循环（1.5s/次），播放后自动开始。

### 6.4 字幕引擎

- 原文/译文各自增量缓冲，共用一条 streaming entry（直接改 `Text.nodeValue`，零 innerHTML/零 DOM 重建）；
- 提交规则：译文句末标点（且原文句末或译文足够长）→ 立即提交；下一片段到来时若上一句已带句末标点自动收口；静音 1.5s；单行 ≥90 字兜底；`turnComplete`/`interrupted` 强制提交；
- 同语言 echo 去重：原文与译文完全一致时隐藏原文行；
- 显示模式：双语 / 仅译文 / 仅原文（浮窗 ⚙️ 内即时切换）。

### 6.5 UI 与设置

- 状态栏改为"连接状态点 + 文本 + 独立音量条"，彻底消除 500ms 闪烁；
- 浮窗新增显示模式选择；`hostEl.dataset.glt*` 暴露诊断字段（供 E2E/排障读取）；
- 设置页：v1.0.5 模型默认、**「测试节点连接」**按钮（真实 WebSocket 握手 + setupComplete 耗时）、旧 2.x 模型配置迁移；

## 7. 踩坑记录

### 7.1 官方文档 WebSocket 示例是错的

把三个配置全塞进 `generationConfig` 会被真实服务端 1007 拒绝。若直接照抄官方文档开发，会得到"握手成功但无输出"或"直接 1007"的假象。**教训：官方文档示例也要用真实服务端验证层级。**

### 7.2 `realtimeInput.audio` 的隐形陷阱

语法合法、握手正常、偶尔出字，但与 `mediaChunks` 同配置对照差 15 倍产出（2 vs 30 条/120s）。这是本次最隐蔽的坑，也是前任所有修复都失效的关键之一。

### 7.3 两点 diff 的"净零变化"陷阱

v1.0.0 与 v1.0.4 的最终 diff 中协议差异为 0（v1.0.1 先加、v1.0.3 后删）。只看最终 diff 会完全错过病因。**教训：多版本故障必须逐 tag diff（版本考古），不能只对比首尾。**

### 7.4 Chrome↔Cloudflare 的 TUN/fake-ip 抖动

本机 Mihomo TUN 导致 Chrome 默认解析路径建连 1.2~8s 抖动、偶发 21s/1006，一度被误判为扩展/网关故障。用页面直接建 WSS + CDP Network 抓完整握手头才排除 Origin/Cloudflare 拦截；用 DoH 真实 IP 映射后稳定 0.5~0.9s。**教训：端到端测试必须把"环境网络"作为独立变量验证。**

### 7.5 E2E harness 日志背压导致的"假卡死"

启用 `contextWindowCompression` 后服务端返回的 24kHz `inlineData` 音频帧变大变多，harness 把每帧 16KB base64 全量写 JSONL 导致内存/日志背压，看起来像"跑挂在 125s"。实际扩展与摄像头正常，改为折叠 inlineData 为摘要（`--log-ws-payload=0|preview|full`）后恢复正常。**教训：观测工具本身也可能成为故障源。**

### 7.6 编码类问题

- PowerShell 5.1 风格环境读取 UTF-8 源文件时中文会被按 ANSI 解码 → `ConvertFrom-Json` 误报 JSON 无效；解决：统一 `[System.IO.File]::ReadAllText(path, UTF8)`；
- 从 devsite HTML 提取代码块时 span 被逐 token 换行，需用 `text_content()` 拼接；
- 发布脚本安全扫描最初把 LICENSE 里的作者名 `Charioteer71` 当私有端点误报，改为精确匹配 `charioteer71.xyz`。

### 7.7 Node 内置 WebSocket 在网关上的 1006

Node 24 自带的 undici WebSocket 直连该网关 100% `close 1006`（10.7s 后 processResponse 报错），改用 `ws@8` 包后正常；而 Chrome 浏览器原生 WebSocket 无此问题。**教训：探针工具与浏览器网络栈行为可能不同，协议结论要以浏览器侧复核。**

### 7.8 git push 凭据限制

本环境无交互式凭据，`git push` 无法完成（credential manager 需要用户在桌面确认）。本地 commit/tag 已就绪，用户本机执行 `git push origin master` 与 `git push origin v1.0.5` 即可。

## 10. 经验与方法论

1. **文档不是真相，服务端才是**：官方 WebSocket 示例的 setup 层级是错的；必须以真实服务端 A/B 裁决。
2. **同配置 A/B 是发现"隐形字段"的唯一手段**：`realtimeInput.audio` 语法合法、行为错误，只有对照 `mediaChunks` 才能暴露。
3. **多版本故障要做版本考古**：先加后删会在首尾 diff 中"净零"，逐 tag diff 才能锁定回归点。
4. **区分"会话死"与"产出退化"**：长会话退化时 WS 一直 alive、状态正常，只有统计每 10s 产出量才能发现；对策要分层（重连换 Key + 看门狗）。
5. **连接不确定性要做故障注入**：慢握手/断网注入能精确验证超时与重连策略，比"偶发观察"可靠得多。
6. **端到端验证必须隔离环境变量**：TUN/fake-ip、CDN、代理都可能制造假故障；先证网络，再证扩展。
7. **观测工具会反噬**：全量记录 16KB 音频帧导致 harness 假卡死，提醒监控/日志本身要有采样与折叠策略。
8. **发布纪律**：白名单打包、版本一致性校验、出包前后安全扫描，一个都不能省。
9. **并行协作靠边界**：写作用域隔离 + 任务板 + 证据落盘，才能让 3 条战线同时推进而不互相踩踏。

## 11. 遗留问题与后续建议

1. **上游 Key 质量波动**：v1.0.5 用看门狗重连换 Key 兜底（可能造成 1~3s 短暂停顿是设计内行为）；若想彻底消除，需要在网关侧做 Key 质量探测/熔断或固定高质量 Key。
2. **DRM（EME）视频**：受保护媒体无法通过 `MediaElementAudioSourceNode` 捕获；后续可评估 `chrome.tabCapture` + offscreen 方案（也是解决复杂站点/X Space 类音频的通用路径）。
3. **AudioWorklet 迁移**：当前 `ScriptProcessor` 兼容性最好但已废弃；后续可迁移到 AudioWorklet（16k worklet + monitor context），降低主线程抖动。
4. **sessionResumption**：翻译模型是否支持尚未验证；若支持，可替代 9 分钟定时轮转。
5. **语境模式**：原生翻译模型无 instruction 通道；可考虑的替代路径是术语表/热词（类似 viitor 的 hotword 模式）或独立后处理，需另行评估延迟与额度。
6. **GitHub 同步**：本地 commit/tag 已就绪，需用户本机凭据执行 push。

## 附录 D：推荐协议与参数速查

### D.1 最终采用的 setup 载荷（实测可用）

```json
{
  "setup": {
    "model": "models/gemini-3.5-live-translate-preview",
    "generationConfig": {
      "responseModalities": ["AUDIO"],
      "translationConfig": {
        "targetLanguageCode": "zh-Hans",
        "echoTargetLanguage": true
      }
    },
    "inputAudioTranscription": {},
    "outputAudioTranscription": {},
    "contextWindowCompression": { "slidingWindow": {} }
  }
}
```

### D.2 音频帧（实测唯一连续）

```json
{"realtimeInput":{"mediaChunks":[{"mimeType":"audio/pcm;rate=16000","data":"<base64 3200B>"}]}}
```

- 16kHz / 16bit / 单声道 / 小端；100ms 一帧（1600 采样）；
- **不要**用 `realtimeInput.audio`（实测稀疏）；
- 不要向 native 翻译模型发 `systemInstruction`（无效）或 `clientContent`（1007 断会话）。

### D.3 扩展关键参数

| 参数 | 值 |
|---|---|
| 握手超时 | 30s（分层） |
| 重连退避 | 600ms→8s 封顶 + 抖动，无限次 |
| 看门狗 | 无转写 18s / 译文停 20s / 服务端静默 45s |
| 会话轮转 | 9 分钟无缝 |
| 音频块 | 1600 采样 / 100ms / 16kHz / 16bit |
| 背压阈值 | `bufferedAmount > 1MB` 丢最旧 |
| 字幕断句 | 标点 / 原文句末 / 静音 1.5s / 90 字兜底 |
| 目标语言码 | `zh-Hans`、`zh-Hant`、`en`、`ja`、`ko`、`es`、`fr`、`de`、`ru`、`pt-BR` 等 |
